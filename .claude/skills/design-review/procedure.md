仕様書承認後、実装に入る前に Pencil MCP を使って画面デザインを作成し、ユーザーとレビュー・修正を行う手順：

## 前提条件

Pencil MCP サーバーが起動していること。利用できない場合は、以下を案内する:
1. Pencil のインストール: https://docs.pencil.dev/getting-started/installation
2. MCP連携の設定: https://docs.pencil.dev/getting-started/ai-integration
3. セットアップ完了後にこのスキルを再実行する

ユーザーがこのフェーズのスキップを希望した場合は、スキップして次のスキルに進む。

## Phase 1: デザイン要件の抽出

1. `@docs/spec.md` を `read` で読み込み、以下のセクションからデザイン要件を抽出する:
   - **グローバルレイアウト**: 共通レイアウト、共有コンポーネント（ヘッダー、サイドバー等）
   - **ロール別画面一覧**: ロールごとのアクセス可能画面とパス
   - **画面別詳細仕様**: 各画面の表示要素、操作、レイアウト構成
   - **インタラクション仕様**: 複雑なUI挙動（D&D、リアルタイム更新等）
   - **データ可視化仕様**: グラフ種別、表示内容、集計ロジック
   - **ユーザーフロー**: 画面遷移の流れ
   - **空の状態・エッジケースのUI**: Empty State、エラー時、ローディング時のUI
   - **競合分析**: 参考にすべきUI/UXパターン
2. デザイン対象の画面一覧をロール別に整理し、ユーザーに提示する:
   - 各画面の役割と主要な表示要素を簡潔に説明する
   - ユーザーと優先順位を決める（最も重要な画面から着手する）

## Phase 2: デザインディレクションの決定

ユーザーの抽象的なデザインイメージを具体的なスタイルに落とし込む。

### Step 1: デザインの方向性をヒアリング

ユーザーに以下を確認する:
- デザインの雰囲気やキーワード（例: 「モダン」「温かみ」「プロフェッショナル」「ミニマル」）
- 参考にしたいサイトやアプリのURL（任意）
- ブランドカラーやフォントの希望（任意）

参考URLが提供された場合は `WebFetch` で分析し、色使い・余白感・角丸・シャドウ・タイポグラフィの特徴を抽出する。

### Step 2: デザイン軸ごとのビジュアルサンプル提示

以下の各軸について、選択肢ごとのビジュアルサンプルを `batch_design` で作成し、`get_screenshot` でユーザーに提示する。ユーザーは見比べて選択する。

サンプルには共通のUI要素（カード、ボタン、入力欄、リスト等）を使い、軸の違いが視覚的に明確になるように作る。

| 軸 | 選択肢 | サンプルで表現する違い |
|---|---|---|
| **色温度** | クール / ニュートラル / ウォーム | 同じカードを3つの配色で並べて表示 |
| **情報密度** | コンパクト / バランス / ゆったり | 同じリストを3つのスペーシングで表示 |
| **装飾レベル** | ミニマル / 適度 / リッチ | ボーダーのみ / 控えめシャドウ / グラデーション+深いシャドウ |
| **角丸** | シャープ(2px) / 標準(8px) / 丸み(16px) | 同じボタンとカードを3つの角丸で表示 |
| **シャドウ** | フラット / 控えめ / 立体的 | 同じカードを3段階のシャドウで表示 |
| **タイポグラフィ** | 均一 / コントラスト強め | 見出し+本文+補足テキストの組み合わせを2パターン表示 |

Step 1 でユーザーのキーワードや参考URLから推定できる軸は、推定値をデフォルト選択として提示する（例: 「モダン」→ クール・ゆったり・ミニマル・標準角丸）。ユーザーはデフォルトを承認するか、サンプルを見て変更する。

### Step 3: デザイントークンの設定

確定したデザインディレクションに基づき、実装で使用する技術スタックのデザインシステムに準拠したトークンを設定する。

1. `@rules/tech-stack.md` を `read` で確認し、UIライブラリとスタイリング手法を把握する
2. プロジェクトルートに `designs/` ディレクトリを作成し、`.pen` ファイルを配置する
3. Pencil MCP の `set_variables` で、Step 2 の選択結果を反映したトークンを設定する:
   - **カラーパレット**: shadcn/ui の CSS変数（`--background`, `--foreground`, `--primary`, `--secondary`, `--muted`, `--accent`, `--destructive` 等）に、選択した色温度を反映した値を設定する
   - **スペーシング**: 選択した情報密度に応じて Tailwind のスペーシングスケールを調整する（コンパクト: 基本3, バランス: 基本4, ゆったり: 基本6）
   - **角丸**: 選択した角丸値を `--radius` に設定する
   - **フォント**: システムフォントスタック（`Inter` or `sans-serif`）
   - **シャドウ**: 選択したシャドウレベルに応じた値を設定する
4. ユーザーが変更した場合、実装時に `tailwind.config.ts` と `globals.css` の CSS変数に反映する旨を伝える

## Phase 3: 全画面のデザイン作成

Phase 1 で決めた優先順位に沿って、全画面のデザインを作成する。この Phase ではユーザーへの確認は行わない。

### デザイン原則

要素を機械的に並べるのではなく、以下の原則に従って意図のあるデザインを作る:

- **視覚的階層**: 画面内の要素に明確な優先順位をつける。主要アクション・重要データは大きく/太く/色で強調し、補助的な情報は控えめにする。すべてを同じサイズ・ウェイトで並べない
- **コントラスト**: 大と小、密と疎、カラーとモノトーンのメリハリを意識する。隣接する要素が同じ視覚的重みにならないようにする
- **余白の意図**: 余白は「何もない場所」ではなくグルーピングと呼吸のためのデザイン要素。関連する要素は近づけ、異なるセクションは十分な余白で分離する。全体を均等スペーシングにしない
- **フォーカスポイント**: 各画面に1つ、ユーザーの視線が最初に向かう場所を設計する。ダッシュボードなら最重要KPI、一覧画面なら検索/フィルタ、詳細画面なら主要コンテンツ
- **コンポーネントのカスタマイズ**: shadcn/ui のデフォルトをそのまま使わず、画面の文脈に合わせてサイズ・カラーバリアント・アイコン付与等を調整する

### 作成手順

画面ごとに以下を実行する:
1. 仕様書の「画面別詳細仕様」と「インタラクション仕様」から、その画面でデザインすべき状態を洗い出す:
   - **デフォルト状態**: 通常のデータが表示されている状態
   - **空の状態**: データ未登録時（Empty State + CTA）
   - **ローディング状態**: データ取得中（Skeleton 表示）
   - **エラー状態**: API失敗時（エラーメッセージ + リトライ）
   - **モーダル・ダイアログ表示中**: 作成/編集/削除確認等のオーバーレイが開いている状態
   - **ステータス別の表示切り替え**: 要素の状態による表示差異（例: 有効/停止中/期限切れ）
   - **データ量による変化**: 大量データ時のページネーション・スクロール表示
   - **権限による表示差異**: ロールによってボタンやメニューの表示/非表示が異なる場合
   上記すべてが該当するわけではない。仕様書に記載のある状態のみを対象とする。
2. `batch_design` で各状態のUI要素を配置する。キャンバス上の配置は以下のルールに従う:
   - **同一画面の状態バリエーションは横並びにグルーピングする**（デフォルト → 空 → エラー → モーダル表示中 等）
   - **画面ごとのグループ間には十分な余白を空けて視覚的に分離する**
   - **各デザインの上部に画面名と状態名を日本語のラベルとして配置する**（例: 「ダッシュボード — デフォルト」「ダッシュボード — 空の状態」）
   - 仕様書のページ構成・レイアウト指定に従う
   - 基本方針: UIライブラリのコンポーネント（shadcn/ui の Button, Input, Card, Dialog 等）と Phase 2 で確定したデザインディレクション・トークンで構成する
   - 上記デザイン原則に従い、視覚的階層とコントラストを意識して配置する
   - Phase 2 で選択した色温度・情報密度・装飾レベル・角丸・シャドウ・タイポグラフィの方向性を一貫して適用する
   - **カスタムデザインが必要な場合**: ヒーローセクション、イラスト、独自アニメーション等、ライブラリ標準では実現できない表現が必要な場合は、ユーザーに確認した上で採用する。カスタム要素は `designs/assets/` に素材を保存し、`designs/custom-styles.md` に実装仕様を記録する（後述）
   - **テキストのオーバーフロー防止**: テキストがコンテナの境界をはみ出さないようにする。長いテキストにはテキストの切り詰め（truncate）や折り返し（wrap）を適用し、コンテナのサイズはコンテンツ量に対して十分な余裕を持たせる
3. 全画面・全状態の作成が完了したら Phase 4 に進む

## Phase 4: 仕様書準拠チェック

ユーザーに見せる前に、`@docs/spec.md` と照合して2段階の自己検証を行う。各段階で不備があれば `batch_design` で修正してから次に進む。

### Level 1: 全体構成チェック

画面設計全体として仕様を満たす構成になっているかを検証する:
- 仕様書に記載された全画面がデザインに存在するか（画面の過不足）
- ユーザーフローの全遷移パスに対応する画面・状態が揃っているか
- 共有要素（サイドバー、ヘッダー、フッター、ナビゲーション）が全画面で一貫しているか
- `snapshot_layout` で全体のレイアウト構造を確認し、画面間の不整合がないか

不足画面があれば追加作成し、共有要素の不整合があれば統一してから Level 2 に進む。

### Level 2: 各画面詳細チェック

各画面を1つずつ仕様書と照合し、詳細な漏れを検証する:
- 仕様書に記載された全UI要素（ボタン、入力欄、ラベル等）がデザインに含まれているか
- ページ構成・レイアウト指定通りに配置されているか
- Phase 3 で洗い出した全状態（デフォルト・空・ローディング・エラー・モーダル表示中・ステータス別等）のデザインが揃っているか
- ユーザーフロー上の遷移トリガー（リンク、ボタン等）が漏れていないか
- 受け入れ基準に記載されたUI上の条件を満たしているか

## Phase 5: ユーザーレビュー

Phase 4 の検証を通過したデザインを、画面ごとにユーザーに提示してレビューを受ける:

1. **プレビュー提示**: `get_screenshot` でデザインのプレビューを取得し、ユーザーに見せる
2. **フィードバック収集**: ユーザーに以下の観点で確認を求める:
   - レイアウトや要素の配置は適切か
   - 情報の優先順位は正しいか
   - 操作フローに違和感はないか
3. **修正**: フィードバックに基づいて `batch_design` で修正する
4. **承認**: ユーザーがOKを出すまで 1〜3 を繰り返す
5. 次の画面に進む

## Phase 6: カスタム素材のエクスポート

デザインにカスタム要素（独自の画像・イラスト・アイコン・アニメーション等）が含まれる場合、実装で使用できる形式で保存する。カスタム要素がない場合はこの Phase をスキップする。

1. `designs/assets/` ディレクトリに素材を保存する:
   - **画像・イラスト**: SVG（ベクター）または PNG/WebP（ラスター）でエクスポート
   - **アイコン**: SVG で統一。命名は `icon-[name].svg`
   - **ロゴ**: SVG + PNG（favicon用）を用意
2. `designs/custom-styles.md` を作成し、標準コンポーネント外のカスタムスタイルを記録する:
   - カスタムカラー（トークン外の色を使う場合、CSS変数名と値）
   - カスタムアニメーション（トリガー、duration、easing の仕様）
   - カスタムフォント（Webフォントの場合、読み込み方法を含む）
   - グラデーション、背景パターン等の装飾
3. 各素材がどの画面のどの要素で使用されるかを `custom-styles.md` に記載する

### ディレクトリ構成
```
designs/
  *.pen                      ← Pencil デザインファイル
  assets/                    ← カスタム素材（画像・アイコン等）
    icon-[name].svg
    hero-[name].svg
    ...
  custom-styles.md           ← カスタムスタイル仕様（任意）
```

## Phase 7: 最終確認・承認

1. 全画面のデザインを一覧で提示し、以下を確認する:
   - 全体の統一感（色、フォント、スペーシング）
   - ユーザーフロー通りの画面遷移が成立するか
   - 仕様書の UI/UX 要件を全て満たしているか
   - カスタム素材がある場合、`designs/assets/` の内容が実装に十分か
2. ユーザーの最終承認を得る
3. 承認後、`designs/` ディレクトリの成果物が実装時の参考となる旨を伝え、次のスキルに進む:
   - `.pen` ファイル: 画面デザインの参照
   - `assets/`: 実装時に `public/` へコピーして使用
   - `custom-styles.md`: カスタムスタイルの実装仕様
