`@docs/spec.md` に新しい仕様書が提供された際の動作手順：
- `read` を使用して、仕様書の全コンテキストと受け入れ基準を完全に理解する。
- `ls -R` を実行し、この変更によって影響を受ける既存のファイル構造を把握する。
- `.claude/tasks/` に `.tasks.md` ファイルを作成（または更新）する。

## タスク分解のルール

タスクは必ず **Phase A（フロントエンドデモ）** と **Phase B（バックエンド統合）** の2フェーズに分割する。

### Phase A: フロントエンドデモ
モックデータで画面が動作する状態を目指す。API・DBは構築しない。

**開始時:** @skills/scaffold-frontend/SKILL.md を実行してフロントエンドプロジェクトを初期化する。

タスク順序:
1. 共有型定義（フロントエンド・バックエンドで共有する型を `lib/types/api.ts` に定義）
2. モックデータ作成（各リソースのファクトリ関数を作成し、固定データを返す）
3. API関数のモック実装（`api/` に関数を作成し、モックデータを返す。将来の実API差し替えを前提としたインターフェースにする）
4. Hook 実装（モックAPI関数を呼び出す形で TanStack Query のHookを実装）
5. View コンポーネント実装（`designs/` 配下の全成果物 — `.pen` デザイン、`custom-styles.md`、`assets/` の画像・アイコン — を参照し、忠実に再現する）
6. Container コンポーネント実装（Hook と View を接続）
7. ページ・ルーティング構成
8. テスト作成（Viewテスト・フロントエンド統合テスト）

**Phase A 完了条件:** `npm run build` と `npm run test` が通り、Playwright 動作確認で全項目パスする状態。

### Phase B: バックエンド統合
Phase A のモックを実APIに差し替え、DB・バリデーション・エラーハンドリングを実装する。

**開始時:** @skills/scaffold-backend/SKILL.md を実行してバックエンド環境を初期化する。

タスク順序:
1. DBスキーマ（Prisma）
2. Repository 実装
3. Service 実装（ビジネスロジック）
4. Validator 実装（Zod スキーマ）
5. Route Handler 実装（API エンドポイント）
6. API関数を実APIに差し替え（Phase A で作成したモック実装を、実際のfetch呼び出しに置換）
7. テスト作成（バックエンド統合テスト・Validatorテスト）

**Phase B 完了条件:** `npm run build` と `npm run test` が通り、Playwright 動作確認で全項目パスし、モックデータが全て実DBに置き換わっている状態。

## 動作確認チェックリストの生成

タスクファイル（`.tasks.md`）に、各フェーズの動作確認チェックリストを含める。仕様書のユーザーフロー・受け入れ基準・画面別詳細仕様から項目を導出する。

### Phase A チェックリスト（フロントエンド）
以下の観点で項目を生成する:
- 全画面への遷移（ナビゲーション・リンクが正しく動作する）
- デザインとの一致（`designs/*.pen` と実装の見た目が一致している）
- 各画面の状態表示（空の状態・ローディング・エラー状態が正しく切り替わる）
- フォームの入力・バリデーション（必須項目、エラーメッセージの表示）
- インタラクション（ボタン・モーダル・ドロップダウン等の操作が正しく動作する）
- 仕様書の主要ユーザーフロー（各フローを端から端まで操作できる）

### Phase B チェックリスト（バックエンド統合）
Phase A の項目に加え、以下の観点を追加する:
- 実データでのCRUD操作（作成・読取・更新・削除が正常に動作する）
- データの永続化（ページリロード後もデータが保持されている）
- エラーハンドリング（API エラー時に適切な通知が表示される）
- バリデーション（無効な入力が拒否され、エラーメッセージが表示される）

## ユーザーへの提示

- Phase A と Phase B を分けて提示し、各フェーズのタスクリスト・動作確認チェックリストを承認してもらう。
- **Phase A 完了後にユーザーにデモを確認してもらう。** フィードバックがあれば Phase B 開始前に修正する。
- 実装を開始する前に、分解したタスクリストをユーザーに提示し、承認を得る。
